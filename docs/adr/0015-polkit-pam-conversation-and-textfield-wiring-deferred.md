# Polkit's PAM conversation and textfield/IPC wiring are deferred, not built

Phase 5's diagram (`build-steps.md`) draws the full path: a privileged action triggers a polkit authorization request, the Supervisor pushes challenge metadata over IPC to the Lua VM dialog, the user types a password into a `secure_submit` `textfield`, and the resulting `SecureBuffer` feeds a PAM conversation that answers polkitd back. Two links in that chain don't exist yet, and building them now would mean guessing at interfaces nothing else in the codebase defines:

1. **PAM.** No PAM crate is in the dependency tree. Driving a real `pam_conv` (prompting, reading the response, handling `PAM_SUCCESS`/failure, then replying to polkitd via `AuthenticationAgentResponse2`) is a substantial, separate concern from the D-Bus handshake itself, and this phase's spec text only asks for the handshake and the buffer type -- not authentication.
2. **`textfield` / IPC envelope attachment.** ADR-0005 describes the Renderer's IPC layer attaching a `SecureBuffer` to a capability/action envelope, and Phase 5's diagram shows the Supervisor pushing challenge metadata to the Renderer over that same IPC layer. Neither the `textfield` scene node nor the Unix socket server that would carry that traffic exists yet -- the scene graph layout engine and `main.rs`'s "Unix socket server, core event loop" (Phase 7/8) are both later phases. There's nothing on either end to attach to.

Decision: `supervisor/src/dbus/polkit.rs`'s `AuthenticationAgent::begin_authentication` is a real, dispatchable D-Bus method (correctly typed, correctly wired into `supervisor::main` against the live session bus) that forwards the parsed `BeginAuthenticationCall` over an `mpsc` channel instead of driving PAM. `main()` drains that channel with a log line (`eprintln!`) as the ceiling until Phase 7/8's event loop exists to push it to the Renderer instead. `cancel_authentication` is a no-op past dispatching correctly, for the same reason -- there's no in-flight PAM conversation to cancel yet.

`shared::SecureBuffer` (ADR-0014) is built and tested but not constructed or consumed anywhere in production code this phase -- it has no `textfield` write site and no PAM read site to attach to yet.

Upgrade path, in order: (a) the Unix socket server and event loop (Phase 7/8) give `main()` something real to push challenges through instead of `eprintln!`; (b) the scene graph's `textfield` node and its `secure_submit` wiring (ADR-0005) give the Renderer side a place to fill a `SecureBuffer` from keystrokes and send it back; (c) a PAM crate (likely `pam-client` or hand-rolled FFI against `libpam`, unresearched -- that choice belongs to whichever phase actually does this) replaces `begin_authentication`'s channel-forward with a real conversation, consuming the `SecureBuffer` that arrives over IPC and calling `zbus_polkit`'s `Authority::authentication_agent_response2` with the result.

This does not contradict ADR-0005 or ADR-0009: both describe the target shape once the scene graph and IPC layer exist, and neither is built or wired against here.

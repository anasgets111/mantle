# `audio.apps` push to Lua is deferred, not built

Phase 6's diagram (`build-steps.md`) draws the full path: PipeWire registry events feed the app-stream mixer, and the resulting list gets "pushed to Lua" so per-app volume sliders can render it as `audio.apps`. That last link doesn't exist yet, same situation ADR-0015 hit for polkit's challenge metadata: there is no IPC socket server and no Lua VM anywhere in this codebase yet (both are Phase 7/8+). There's nothing on the other end to push to.

Decision: `supervisor/src/audio/mixer.rs::run` is a real, dispatchable PipeWire registry listener -- correctly filtered to `Stream/Output/Audio` nodes, correctly resolving the owning pid (see docs/adr/0016-pipewire-app-stream-pid-uses-application-process-id-not-sec-pid.md), correctly reacting to node-added, node-properties-changed, and node-removed events with zero polling. It forwards each updated snapshot (`Vec<AppStream>`) over a `tokio::sync::mpsc::UnboundedSender` instead of writing anywhere Lua could read it. `supervisor::main` drains that channel alongside the existing polkit challenge channel via `tokio::select!` and logs each update (`eprintln!`) as the ceiling, mirroring the exact pattern ADR-0015 established for polkit.

Also deferred, per the same phase's own scope: `audio:set_app_volume`, `audio:set_app_muted`, master `audio.volume`/`audio.muted`, default sink/source routing, and BlueZ codec control (`docs/oblisk-supervisor-services-dbus.md` §5.3/§6 describe these). Phase 6's two goals are read-only registry mapping; none of the write paths are built, and `AppStream` carries no `volume`/`muted` fields since nothing populates them yet -- adding unpopulated fields for a future phase's sake would just be dead struct surface.

Upgrade path, in order: (a) the Unix socket server and event loop (Phase 7/8) give `main()` something real to push snapshots through instead of `eprintln!`; (b) the Lua VM's `audio.apps` signal table (`docs/oblisk-supervisor-services-dbus.md` §6.2) gives the Renderer/Lua side a place to receive them; (c) `audio:set_app_volume`/`set_app_muted` and the `AppStream` fields they need are separate work once SPA `Props`/`Route` parameter parsing exists in this module -- unresearched here, deliberately out of scope for a read-side tracking phase.

This does not contradict `docs/oblisk-hardware-event-pipeline.md` §2 or `docs/oblisk-supervisor-services-dbus.md` §6: both describe the target shape once the IPC layer and Lua VM exist, and neither is built or wired against here.

# Depend on smithay-client-toolkit instead of hand-dispatching Wayland protocols

`build-steps.md` Phase 1's renderer `Cargo.toml` listed raw `wayland-client`, `wayland-protocols-wlr`, and `wayland-protocols`, with no dependency on `smithay-client-toolkit` (SCTK). Phase 3 then pointed at SCTK's own EGL setup code as something to read and copy from. As spec'd, Oblisk planned to hand-roll registry binding, layer-shell surface creation, and presentation-feedback dispatch using the same low-level crates SCTK is already built on top of, instead of depending on SCTK directly.

Checked SCTK's source directly (`Smithay/client-toolkit`, not from memory): `src/shell/wlr_layer` wraps `zwlr_layer_shell_v1`/`zwlr_layer_surface_v1`, `src/presentation_time.rs` wraps `wp_presentation`/`wp_presentation_feedback` with a typed `feedback()` call (exactly the evidence mechanism ADR-0003 depends on), `src/session_lock` wraps `ext_session_lock_v1`, `src/foreign_toplevel_list.rs` and `src/output.rs` cover active-window and output tracking, `src/seat` bundles keyboard/pointer handling with `xkbcommon`. That's nearly every Wayland-facing protocol the Renderer needs, already typed and delegate-dispatched, maintained by the same team that maintains `wayland-client` itself.

Decision: the renderer depends on `smithay-client-toolkit` directly and uses its `wlr_layer`, `presentation_time`, `session_lock`, `foreign_toplevel_list`, `output`, and `seat` modules. Raw `wayland-protocols` stays only for `wp-text-input-v3` (the `textfield` primitive's IME binding), which SCTK does not wrap. This is a direct application of the project's own rule: if an installed dependency already solves it, use it rather than reimplementing it on top of the same lower-level crate.

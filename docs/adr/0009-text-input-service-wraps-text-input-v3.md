# A TextInputService owns text-input-v3, textfield nodes never touch the protocol

`textfield` (IDL §5.2) is IME-aware and maps to `wp-text-input-v3`, but neither SCTK nor any other maintained crate wraps it: `wayland-protocols` only exposes the raw generated `zwp_text_input_v3` client bindings, gated behind its `unstable` feature. Something has to own the `Dispatch<ZwpTextInputV3, D>` impl and the raw `enter`/`leave`/`preedit_string`/`commit_string`/`delete_surrounding_text`/`done` event sequence.

Checked Noctalia's implementation (`src/wayland/text_input_service.h`, `src/ui/text_input_client.h`) rather than design this from scratch. Their shape: one `TextInputService` per seat owns the protocol object and every raw event end to end. Scene nodes never see the protocol; they implement a narrow `TextInputClient` interface instead: report state (surrounding text, cursor, `purpose`, a `sensitiveData`/`hiddenText` flag) and receive an edit as a batched diff (`commitText`, `preeditText`, `deleteBeforeLength`/`deleteAfterLength`), not raw keystrokes. This matters because real IME composition (CJK input, for instance) doesn't work character-by-character; a diff is the only representation that's actually correct.

Decision: the renderer gets one `TextInputService` bound to the seat, and each `textfield` scene node implements the equivalent of `TextInputClient` on the Rust side. `on_change` fires from the edit diff (effectively on the protocol's `done` event), not per keystroke. `oblisk-idl-api-specs.md` §5.2's wording is now corrected to match.

Composition with SCTK (ADR-0008): no second event loop. SCTK's `calloop` feature already drives one `wayland_client::EventQueue` via `calloop-wayland-source`, and the app's top-level state struct already implements `Dispatch<T, D>` for SCTK's delegated types through its `delegate_*!` macros. `Dispatch<ZwpTextInputV3, D>` for `TextInputService` is hand-written but slots into that same struct and the same queue; `zwp_text_input_manager_v3::get_text_input(seat)` takes the `wl_seat` SCTK's own `seat` module already provides. One dispatch table, no bolt-on thread.

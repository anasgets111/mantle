# Revision is tracked per capability, fed by inbound state pushes

Write calls take bare unwrapped values (`audio:set_volume(vol)`), not `Signal` handles, so `expected_revision` can't be read off the write's own arguments the way `generation_id` rides the mlua wrapper. Considered stamping a per-capability "last observed revision" table on every `Signal:get()` call instead. Rejected: a zero-argument write like `audio:toggle_mute()` has no `:get()` in its own callback to stamp anything, leaving the table's freshness dependent on unrelated reads elsewhere in the frame.

Instead: the Renderer's IPC receive loop keeps one revision counter per capability, bumped on every inbound `StateSnapshot` (`shared::StateSnapshot { revision, payload }`, already defined in `build-steps.md` Phase 2) regardless of whether any Lua code ever reads the corresponding signal. The write envelope reads that counter directly. Matches the envelope's existing `capability`-scoped `expected_revision` field exactly: one counter per capability, not per signal, no new wire format needed. Checked Quickshell and Noctalia for prior art here; neither has anything resembling optimistic-concurrency on writes, because neither has more than one writer ever active on a capability at once. This mechanism exists purely because Oblisk allows generation N and N+1 to both hold write paths open during a swap.

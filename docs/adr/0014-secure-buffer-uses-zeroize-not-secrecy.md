# SecureBuffer uses the zeroize crate, not secrecy

`build-steps.md` Phase 5 names both `secrecy` and raw pointer zeroing as options for the native buffer typed passwords land in. ADR-0005 already settled the usage shape this buffer has to support: zero the buffer explicitly right after the one sanctioned read (serializing it into an outgoing IPC envelope), with `Drop` only as a backup for the panic/early-return case, not the primary mechanism.

Checked both crates against that shape. `secrecy`'s `SecretBox<T>`/`SecretString` expose `expose_secret()` for the sanctioned read and zeroize automatically on `Drop`, but have no public method to zero the contents on demand while the value is still alive -- the only way to force an early zero is to drop the value, which doesn't fit "zero now, but I still need this binding a moment longer" if a caller ever needs that. `zeroize`'s `Zeroize` trait gives a plain `.zeroize()` method callable at any point, and `ZeroizeOnDrop` (derivable alongside it) adds the `Drop` backup on top -- both halves of ADR-0005's shape from one pair of derives, no extra wrapper type needed.

Decision: `shared::SecureBuffer` (`shared/src/secure_buffer.rs`) wraps a `Vec<u8>` with `#[derive(Zeroize, ZeroizeOnDrop)]`. `push_str` appends one edit diff's UTF-8 bytes (matching ADR-0009's diff-based edit model, not per-keystroke); `expose_secret()` is the one sanctioned read; `.zeroize()` (from the derive) is what a caller invokes right after that read crosses the IPC boundary, with `Drop` zeroizing again as the ADR-0005 backup.

Lives in `shared`, not `supervisor` or `renderer`: the secret originates in the Renderer (`textfield` keystrokes) and is read again in the Supervisor (PAM), so the type has to be constructible and readable from both sides of the IPC boundary it's meant to cross -- putting it in either binary crate would make the other depend on it awkwardly. Neither crate is wired to actually construct or consume one yet; see docs/adr/0015-polkit-pam-conversation-and-textfield-wiring-deferred.md for why.

Test seam: `Vec<u8>::zeroize()` (the trait impl `SecureBuffer` derives from) is documented as "best effort" -- it zeros the initialized elements *and* the Vec's spare capacity, not just the logical length via `.clear()`. `shared/src/secure_buffer.rs`'s unit test proves that distinction for real: it captures the backing allocation's pointer and capacity before calling `.zeroize()`, then reads *past* the new (zero) length into the full capacity and asserts every byte is zero -- not just that `len()` dropped to 0, which a naive `.clear()` alone would also produce while leaving the actual plaintext bytes sitting on the heap. Reading into owned-but-uninitialized capacity this way is defined behavior (`u8` has no invalid bit pattern, the Vec hasn't deallocated); it would not be defined behavior to read the same memory after the buffer is dropped and freed, which is why the `Drop` backup gets a separate test using a different technique: `shared/tests/secure_buffer_drop_zeroizes.rs` installs a `#[global_allocator]` that inspects the exact bytes `dealloc` receives back, filtered by pointer identity (not allocation size, which collides with unrelated allocations elsewhere in the test binary's own harness startup -- a size-only filter was tried first and produced a false-positive failure inside `test::cli::parse_opts`). Same technique `zeroize`'s own test suite (`zeroize-1.9.0/tests/alloc.rs`) uses for the same problem.

Amendment: both scrub points above only ever touch `SecureBuffer`'s *current* backing allocation. `push_str` is called once per edit diff, so it grows more than once per secret, and plain `Vec::extend_from_slice` growth would allocate a new block, copy the old bytes over, and free the old block without zeroing it -- a plaintext prefix left on the heap that neither `.zeroize()` nor `Drop` can reach afterward. `push_str` now manages growth itself: allocate the new block, copy the bytes across, zeroize the old `Vec` in place (safe -- `Vec<u8>: Zeroize` doesn't reallocate), then drop it. `shared/tests/secure_buffer_growth_zeroizes.rs` covers this with the same allocator-hook technique, scanning every freed block for a leaked secret prefix instead of watching one pointer.

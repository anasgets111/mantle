# Polkit agent registration uses zbus_polkit for the Authority proxy, hand-writes the AuthenticationAgent side

`build-steps.md` Phase 5 names the registration method `org.freedesktop.PolicyKit1.Authority.RegisterAgent`. Checked polkit's own source directly (`polkit-org/polkit`, `src/polkit/polkitauthority.c` and the shipped `data/org.freedesktop.PolicyKit1.Authority.xml`), not from memory: the real method is `RegisterAuthenticationAgent`, signature `(subject: (sa{sv}), locale: s, object_path: s) -> ()`, at `/org/freedesktop/PolicyKit1/Authority` on `org.freedesktop.PolicyKit1`. `RegisterAuthenticationAgentWithOptions` also exists (adds an `a{sv}` options dict, e.g. `fallback` for multi-agent setups) but nothing here needs it. `Subject`'s `subject_kind` is one of `unix-session` (`session-id: s`), `unix-process` (`pid: u`, `start-time: t`), or `system-bus-name` (`name: s`) -- checked against the same source.

The interface polkitd calls back into once registered, `org.freedesktop.PolicyKit1.AuthenticationAgent`, is separate and has to be implemented by us: `BeginAuthentication(action_id: s, message: s, icon_name: s, details: a{ss}, cookie: s, identities: a(sa{sv})) -> ()` and `CancelAuthentication(cookie: s) -> ()` (`src/polkitagent/polkitagentlistener.c`).

Checked prior art per `build-steps.md`'s own links: LXQt's agent (`src/policykitagent.cpp`) goes through the `PolkitQt1` C++ wrapper library rather than raw D-Bus, registering at `/org/lxqt/PolicyKit1/AuthenticationAgent` with a `unix-session` subject built from `PolkitQt1::UnixSessionSubject`. AGS's `polkit.ts` predates the project's v2 Vala/Astal rewrite and no longer exists at the linked path; not usable as a reference. Neither changes the verified signature above; the polkit source itself is authoritative.

Also checked crates.io for an installed-dependency fit before hand-rolling the whole client call (AGENTS.md rung 5): `zbus_polkit` (MIT, `dbus2` org -- the same GitHub org that maintains `zbus` itself) ships an `Authority` `#[zbus::proxy]` trait and a matching `Subject`/`Identity` type, at `zbus_polkit = "5.0.0"` against `zbus = "5.0.0"`, satisfying this workspace's `zbus = "5.19.0"`. Its `Authority::register_authentication_agent`/`unregister_authentication_agent` signatures match the verified wire signature exactly. A second crate, `zbus-polkit-agent` (GPL-3.0-or-later), wraps agent-hosting scaffolding, but its license doesn't match this workspace's other dependencies (SCTK, zbus, femtovg are all MIT/Apache-2.0) and pulling it in isn't worth a license mismatch for what turns out to be a handful of lines.

Decision: `supervisor/src/dbus/polkit.rs` depends on `zbus_polkit` (`default-features = false, features = ["tokio"]`, matching this crate's own `zbus` feature set) for the `Authority` proxy and `Subject` type, used directly by `current_session_subject()` and `register_agent()`. The `AuthenticationAgent` side (`BeginAuthentication`/`CancelAuthentication`) has no maintained MIT/Apache crate to reuse, so it's hand-written as a `#[zbus::interface(name = "org.freedesktop.PolicyKit1.AuthenticationAgent")]` impl against the signature verified above.

`current_session_subject()` builds a `unix-session` `Subject` from `$XDG_SESSION_ID` rather than a `unix-process` subject built from this process's own pid -- ponytail: see the function's own doc comment for why (`pam_systemd` sets it for every real session; the logind round-trip to resolve a session id from a pid is the general-purpose upgrade path once this crate has a logind client for some other reason).

Amendment on the test-harness doc: `docs/oblisk-tdd-test-harness.md` §2.2's mock D-Bus example uses `#[dbus_interface]`, zbus 3.x's macro name. Checked the vendored `zbus_macros-5.19.0` and `zbus-5.19.0` source directly: zbus 5.x renamed it to `#[zbus::interface]` (`zbus::lib.rs` re-exports `zbus_macros::interface`, no `dbus_interface` export exists at all). `supervisor/src/dbus/polkit.rs`'s own test module uses the corrected name; that doc's code sample is stale for this project's actual `zbus` major version.

Test seam: both directions of the handshake are exercised over a p2p `zbus` connection (`tokio::net::UnixStream::pair()`, `zbus::connection::Builder::unix_stream(..).p2p()`, no bus daemon, no `Connection::system()` dependency in `cargo test`) -- `zbus`'s own `tests/e2e.rs` (`iface_and_proxy_unix_p2p`) uses the identical pattern, and `zbus`'s `p2p` feature only pulls into this workspace's `[dev-dependencies]`, not the shipped `supervisor` binary. One test exports a mock `Authority` object on the p2p peer and asserts `register_agent()` sends the exact `RegisterAuthenticationAgent` call (subject kind/details, locale, object path) a real `polkitd` would receive. A second and third test export the real `AuthenticationAgent` and assert `BeginAuthentication`/`CancelAuthentication` dispatch correctly from a raw `zbus::Proxy` call standing in for `polkitd`.

# Reload strategy splits on topology change

The original spec ran every config edit through a full generation swap: new process, new Wayland/EGL binding, cross-monitor presentation evidence, then reap. That pays a full process respawn for a one-line color edit. We split reload into two paths: a **value change** (anything not touching a top-level `surface` node's set, layer, anchor, or monitor) does an **in-place reload**: a Lua VM reset and re-run inside the current generation, no new process, no generation ID bump. A **topology change** still goes through the full **generation swap** (candidate spawn, presentation evidence, promote, reap).

Considered keeping the single-path generation swap for everything, for uniformity and one code path to test. Rejected: it makes every keystroke-to-save cycle pay Wayland rebinding and a multi-output presentation-feedback round trip, which is the exact stutter the swap protocol exists to avoid in the first place.

Also considered dropping the process boundary entirely and reconciling one long-lived Wayland connection against a rebuilt scene tree on every reload, matching Quickshell's model: a fresh `QQmlEngine` per reload, with a stable-id-matched `Reloadable` protocol letting components like windows reuse their native handle across the rebuild. Rejected: Quickshell can do that safely because QML's JS layer runs under a tracing GC (QV4), so the old engine's object graph is simply abandoned and reclaimed. Rust has no GC to lean on. Reusing a native surface or texture handle while a new scene tree is built and reconciled against the old one is exactly the class of problem a GC makes safe for free; without one it means unsafe code, `Rc<RefCell<>>` runtime panics, or manual arena and generation tagging. The process boundary buys memory safety instead: killing a process is a kernel-guaranteed single free of everything it owned, no manual proof of dangling aliases required. In-place reload stays safe without a GC for a different reason: it only ever drops the whole `mlua::Lua` VM atomically via RAII, never reconciling a live native object graph in place. That's also why `ProcessHandle` (from `process.run`) defaults to dying with that same VM drop; state the Supervisor holds on a generation's behalf, like idle-threshold registrations, can't rely on the drop alone (ADR-0006).

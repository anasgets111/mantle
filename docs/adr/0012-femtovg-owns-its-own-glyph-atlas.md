# FemtoVG's glyph atlas is used as-is, not bridged from cosmic-text's shaper

`build-steps.md` Phase 4 asks for two things that read as one pipeline: an async wrapper around `cosmic-text`'s shaping (point 1) and "map glyphs to a dynamic, size-bounded GPU texture atlas cache (2048x2048) in FemtoVG" (point 2), with a diagram showing cosmic-text's shaped glyphs flowing into FemtoVG's atlas. Checked FemtoVG 0.26.0's actual source: its glyph-atlas-filling path (`GlyphAtlas::render_atlas`, `femtovg/src/text.rs`) is `pub(crate)` and only accepts `PositionedGlyph`s produced by FemtoVG's own internal shaper (`rustybuzz`/`swash` driven through its own `Font`/`FontFaceRef` types via `Canvas::add_font_mem` + `fill_text`/`measure_text`). There is no public entry point to hand it glyphs shaped by anything else, cosmic-text included. Its atlas pages are also a private fixed `TEXTURE_SIZE = 512` constant that grows by adding further 512x512 pages, not by expanding one fixed 2048x2048 texture — the spec's exact number isn't configurable through any public API either.

Considered reimplementing atlas packing on top of FemtoVG's lower-level `draw_glyph_commands`/`GlyphDrawCommands` to bridge cosmic-text's shaped runs in. Rejected: that means hand-rolling UV/kerning bookkeeping FemtoVG's own (private) atlas code already does correctly, on top of a dependency specifically chosen (Phase 1) because it already solves this — the same "does an installed dependency solve it" rule that picked FemtoVG in the first place argues against duplicating its internals now.

Also considered a narrower version of the same idea: FemtoVG's `Canvas::create_image_empty`/`update_image` are public, so a hand-rolled 2048x2048 atlas could upload cosmic-text/swash-rasterized glyph bitmaps into one persistent GPU texture and draw them via an image-pattern fill, without touching FemtoVG's private text-shaping internals at all — only its own (comparatively small) packing/eviction bookkeeping would need writing. This would satisfy the spec's literal "2048x2048" number where the decision above doesn't. Rejected for now, not as unworkable: there is no scene-graph `Text` node yet to drive a packer's eviction policy against (what gets evicted when the atlas fills, keyed on what usage pattern), so building one today would be sized against a guess rather than a real consumer — exactly the shape of problem AGENTS.md's rung 1 ("does this need to be built at all") asks to hold off on. Revisit this once a real `Text`/`Icon` scene-graph node exists and needs atlas control finer than FemtoVG's own gives (e.g. cross-surface glyph sharing, or eviction tuned to the bar's actual working set).

Decision: cosmic-text's async shaping wrapper (`renderer/src/text/shaping.rs`) and FemtoVG's atlas (`renderer/src/text/atlas.rs`) stay two separate, independently correct pieces for this milestone, not a single bridged pipeline. cosmic-text's `ShapingHandle` is the off-thread measurement/shaping primitive Phase 4 point 1 asks for — genuinely useful on its own to a future layout engine that needs to know how wide a string is before it can lay a `Text` node out. FemtoVG's `Canvas`/`TextPainter` is driven through its own public font/text API for actual GPU rasterization, using its own internal shaper and atlas exactly as it's designed to be used. `ShapingHandle::default_font_bytes()` gives both systems the same font (found once, off-thread, via cosmic-text's `fontdb` discovery) so they at least agree on *what* font is being measured and drawn, without agreeing on *how* it's shaped internally.
